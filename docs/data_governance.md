# Data Governance

## Ownership

Every dataset declares an owner and a classification in the schema registry, and
those values flow into the catalogue (`dataset_catalog`) and the published JSON
contracts. They are not documentation about the code — they *are* the code.

| Dataset group | Owner | Classification |
| --- | --- | --- |
| `agency`, `location` | data-engineering | public |
| `transaction`, `account`, `vendor`, `contract`, `budget`, `department` | data-engineering | internal |
| Gold risk and alert datasets | financial-oversight | internal |
| Quarantine | data-engineering | internal |

## Data classification

Nothing in this platform is confidential, because nothing in it is real. Every
person, vendor, account number and tax identifier is generated by Faker with a
fixed seed. Account numbers are masked at generation (`****1234`) rather than
generated in full and masked later, and tax identifiers deliberately use a
`TX########` shape that cannot collide with a real EIN.

If this platform ingested real data, the classification column is where the
handling rules would attach, and the three that would matter most are already
structurally supported:

- **PII minimisation** — the canonical schemas carry only what the analysis
  needs. There is no date of birth, no full address for individuals, no full
  account number anywhere in the pipeline.
- **Log sanitisation** — the logging processor scrubs any key matching a
  credential pattern (`password`, `token`, `api_key`, `dsn`, …) from every log
  line, so a future `log.info("connecting", **config)` cannot leak one.
- **Field-level lineage** — the schema registry records where each field comes
  from, which is what a data-subject request would traverse.

## Data contracts

Contracts are published as JSON Schema in `schemas/`, generated from the
registry by `python scripts/export_schemas.py`. Each declares the business key,
required fields, closed value sets, numeric bounds, the owner and the version.

Two enforcement paths, deliberately:

| Path | Where | Used for |
| --- | --- | --- |
| Pydantic models | `src/core/contracts.py` | REST and streaming — records arrive individually and are judged individually |
| Vectorised rules | `src/silver/validation.py` | Batch — the same rules as column operations, for speed |

Both produce the same stable error codes, so a rejection means the same thing
regardless of which door the record came through.

`additionalProperties: true` is set on every contract on purpose: an upstream
system adding a field must not break ingestion. New fields land in Bronze
untouched and are promoted to Silver only once declared.

## Schema evolution

Additive changes are absorbed without a migration:

1. Bronze is schema-on-read — a new column is stored as it arrives.
2. The Bronze loader unions schemas across files, back-filling nulls.
3. Silver promotes a column once it is declared in the registry.
4. Records written before the column existed keep a null; nothing is back-filled
   with invented values.

The transaction feed ships in two versions to prove this rather than assert it:
`transactions_2025.csv` (v1.0) and `transactions_2026.csv` (v1.1, adding
`merchant_category`). Both live in one Silver table.
`sql/05_data_quality.sql::schema_version_distribution` reports the split.

Breaking changes — a renamed key, a narrowed type, a removed required field —
are **not** handled automatically, and should not be. They require a new schema
version, a mapping in the reader, and a decision about historical records.

## Lineage

Lineage is emitted by the code that performs each transformation, not
reconstructed afterwards by parsing SQL. Each edge records:

```
source_dataset -> target_dataset
  transformations: [schema_alignment, type_casting, deduplication, ...]
  records_in: 55,550   records_out: 48,464   dropped: 7,086
  pipeline, version, run_id, timestamp
```

Two forms, because they serve different readers:

- `lineage_edges` in the metadata store — per-run, historical, queryable
- `metadata/lineage.json` + `docs/lineage.md` — a reviewable snapshot

The row-count delta is the part that matters during an incident. "What fed this
table?" is answerable from a parser; "where did 7,086 records go?" is not.
`upstream_of()` walks the graph transitively, and `GET /lineage/{dataset}`
serves it.

## Auditability

Every pipeline execution writes a `pipeline_runs` row containing the run id,
pipeline version, config version, model version, seed, engine, host, Python
version, per-stage timings, record counters and final status. The run is
recorded **before** work starts and updated at the end, so a process killed
mid-run leaves a `RUNNING` row that says so rather than no trace at all.

Failures are recorded too. A pipeline that only records successful runs is blind
to exactly the runs worth investigating.

Every record carries `_source_system`, `_source_file`, `_ingestion_run_id`,
`_silver_run_id` and `_record_hash`, so any row in Gold can be traced to the file
it arrived in and the runs that transformed it.

## Retention

| Data | Retention | Reason |
| --- | --- | --- |
| Bronze | Indefinite | The reconstruction source for everything else |
| Silver / Gold | Rebuildable at will | Derived; delete and re-run |
| Quarantine | Indefinite, partitioned by detection date | Recovery and trend analysis |
| Metadata | Indefinite | Small, and it is the audit trail |
| Model artifacts | All versions | Reproducing a past score requires the model that produced it |

The lake is gitignored: it is reproducible from a seed, so committing it would
add megabytes to the repository and prove nothing.

## Access control

Local development runs as one user; the structure for separating access is in
place rather than implemented:

- `docker/postgres/init/01_schema.sql` creates a `fil_readonly` role with
  `SELECT` only, including default privileges for tables created later. Nobody
  should explore metadata with the account the pipelines write with.
- The analytics engine refuses write statements outright — anything that mutates
  the lake must go through a pipeline so lineage and quality metadata are
  recorded.
- The serving API is read-only by construction; CORS is restricted to the
  dashboard origin rather than `*`.
- Secrets come only from the environment. `.env` is gitignored, `.env.example`
  is committed with placeholder values, and no credential appears in
  `config/settings.yaml`.

## Reproducibility

Same seed, same configuration, same output — byte for byte.

| Recorded | Where |
| --- | --- |
| Generation seed | `metadata/generation_manifest.json`, `pipeline_runs.seed` |
| Pipeline and config version | `pipeline_runs` |
| Model version, features, hyperparameters, training window | `model_registry`, `data/models/model_manifest.json` |
| Environment (host, Python, platform version) | `pipeline_runs` |
| Which source files were ingested, and their content hashes | `ingestion_ledger` |

Determinism is enforced where it is easy to lose: all randomness flows through
one seeded generator, deduplication survivors are chosen by a total ordering,
surrogate keys are content hashes rather than sequences, and alert ids are
UUIDv5 over the transaction and rule set so a re-run updates a case instead of
creating a duplicate.

## Quality as a governed asset

Quality results are published into the lake (`gold_data_quality_summary`), not
only into the monitoring database, so an analyst can join *"how much did agency
X spend"* to *"how much should I trust that number"* in one query. Governance
that lives only in a separate tool is governance most people never see.
